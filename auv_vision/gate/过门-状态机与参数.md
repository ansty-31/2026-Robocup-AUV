## 1. 量与符号（读状态表前必须统一）

| 符号 | 含义 | 单位 | 来源 |
|---|---|---|---|
| `z` | 门框中心在**相机系**的深度（≈相机到门平面的距离） | m | `P: tvec.z`；width 档用 `fx·W/Δu` 粗估 |
| `dx_m, dy_m` | 门框中心相对光轴的横向/竖直偏移 | m | `tvec.x, tvec.y`。**2026-09-18 起不再参与控制**（只打印/调试）：深度尺度约 20% 误差，拿它居中等于把尺度误差灌进回路 |
| `dxn, dyn` | **归一化像素**偏差：±1 = 半个画面 | — | `(像素 - 屏中心)/(屏尺寸/2)` |
| `ratio` | 门框 bbox 宽 / 屏宽 | — | `det.w / w` |
| `limit` | 归一化 DOF，`[-1, 1]`；中位 128、幅值 127 字节 | — | `comm.yaml frame` |
| 轴映射 | `axis0=yaw, axis1=surge, axis2=heave, axis3=sway` | — | `comm.yaml dof_map` |

**2026-09-18 起：居中一律按像素算（含位姿档）**（`gate_task.py` `_on_pose`）。位姿只提供**深度 `z` 和"这一帧可信"这个事实**，不再用 `t_x/t_y`(米) 居中。原因（实测）：
1. `t_x/t_y` 与 `z` 同源，深度约 20% 尺度误差会整体灌进横向控制；
2. 米制/像素两套阈值两套 PID 时，`full↔coarse` 交替（实测 43% 帧被 PnP 拒绝）会让**两套控制器各拿一半帧 → 永远收敛不了**（表现为"一直在中心附近 HOLD、调不动"）。
统一后：**一套阈值 `align.px_x/px_y` + 一套 PID（像素那对）覆盖全档位**，切档没有跨量纲 D 尖峰，可用帧数翻倍。

**符号约定（2026-09-18 修正）**：`sway = +PID(dxn)`、`heave = -PID(dyn)`、`yaw = +PID(dxn)`。
**「居中成功」的判据 = 范围 × 帧数**，两者独立：
- **范围**（2026-09-18 三次放宽 + 全档位统一按像素）：`align.px_x/px_y = **0.30/0.26**`（**位姿档同用这套**）、
  coarse `align_x/align_y = **0.33/0.29**`（coarse 的框心是最粗的估计，刻意比它略松）。
  （旧的 `align.xy_m` / `align.scale_m` 已删除；配置里若残留会被忽略，
  用例 `test_pose_path_centers_in_pixels_not_meters` 专门塞 `xy_m=0.001` 证明它不起作用。）

  **基准 = 小球那套实测判据**：`ball.center_eps: 0.25`（`cfg/comm.yaml` ball 段）。撞球要求「正中命中」
  都只用 0.25，而门开口比机身大得多 → 过门取比它更松一档（0.30）；竖向 0.26 略紧（竖向余量只有横向一半，
  且 1 单位 `dyn` = 0.462·z 米、`dxn` = 0.818·z 米 → 等比换算 `dyn ≈ 0.885·dxn`）。

  换算（标定 `cfg/front_camera.yaml`：fx=782.5、fy=779.8、1280×720 → **1 单位偏差 = 0.818·z（横）/ 0.462·z（竖）米**）：

  | 门槛 | z=3.0m | z=1.5m | z=1.0m | z=0.7m（判过门距离） |
  |---|---|---|---|---|
  | `px_x=0.30` | ±74cm | ±37cm | ±24.5cm | **±17.2cm** |
  | `px_y=0.26` | ±36cm | ±18cm | ±12.0cm | **±8.4cm** |

  ### 工作假设集（2026-09-18 定：**暂时无法实测距离，先按它跑通**）

  规则原文（`.docwork_gate/rules.md:97`）只说「门大小为约 70×50cm，红色 PVC 管」，**没说是外轮廓还是开口**。
  按**最保守**读法取假设：

  | 项 | 假设值 | 依据 / 保守性 |
  |---|---|---|
  | 门外轮廓 | 0.70 × 0.50 m | 规则原文 |
  | 管径 | 0.05 m | 常见规格；**实际更细 → 开口更大 → 更安全**（保守） |
  | 开口 | **0.60 × 0.40 m** | 外轮廓 − 2×管径 |
  | 机身穿越截面 | **0.35 × 0.30 m** | 用户口述「**面积不到门框面积一半**」：门框 0.35m² → 机身 ≤0.175m²；这里取**悲观端** 0.105m²（门框的 30%、开口的 44%） |
  | 单边余量 | **横向 12.5cm / 竖向 5.0cm** | (0.60−0.35)/2、(0.40−0.30)/2 |

  ### 门槛 > 余量 ≠ 设错了：门槛不是「穿越时的误差」

  换算到判过门距离 z=0.7m：`px_x=0.30` → 17.2cm（余量 12.5cm，137%）；`px_y=0.26` → 8.4cm（余量 5.0cm，168%）。

  这**不是**参数设错了，因为 `align.px_*` 只是「**开始同时前进+修偏**」的起点误差 —— 流程是
  **居中 → 前进 → 冲刺**，穿越瞬间的误差由 APPROACH 段连续的 sway/heave 闭环决定，而不是这个门槛。

  **这套假设下真正的瓶颈是竖向死区，不是门槛**：上浮侧有效死区 0.138 → 换算到 z=0.7m 就是 **4.5cm**，
  已经吃掉那 5.0cm 余量的 **90%**（下潜侧被 `dof_comp.dive_scale` 放大 → 有效死区 ≈0.069 → 3.2cm）。
  ⇒ **加减 `px_y` 都动不了这个瓶颈**（见下面的决策规则第 4 条）。

  ### 现场调参决策规则（撞了 / 卡了先看这条）

  | 现象 | 拧哪个旋钮 |
  |---|---|
  | 卡在 HOLD 不动、迟迟不进 APPROACH / 一直 REACQUIRE | **放宽** `px_x/px_y`（或 `coarse.align_*`） |
  | 上下蹭杆 | **收紧 `px_y`**：0.26 → 0.22 → 0.20（竖向主旋钮） |
  | 左右蹭杆 / 撞门柱 | **收紧 `px_x`**：0.30 → 0.25；顺带看 `align_yaw` 有没有抖 |
  | 竖直总差几厘米上不去 | **不是门槛**：抬 `ball.pid.kp`（把输出顶出 0.138 死区）或给上浮也加补偿（`dof_comp` 现只作用于 `heave<0`） |
  | 冲刺太快 / 太贴门 | 降 `surge.through`(0.5) 或 `z.cross`(0.7)，与对准门槛无关 |

  以后量到真尺寸（门的**外轮廓 / 开口内缘 / 管径**、机身**含推进器的最大穿越截面**），按同一算式
  （`X = 0.818·z·dxn`、`Y = 0.462·z·dyn`）重算这张表并回填。

  #### PnP 深度 +20% 偏置：**已知，暂不处理**（不阻塞调参）

  - **观测**（实跑日志，`tools/analyze_task_log.py`）：PnP 解出的 `z` 比「bbox 宽度粗估」
    （`fx·W/Δu`，`W = geometry.frame_w = 0.70`）**大约 20%**。
  - **最省事的解释**：模型四角若标在**开口内缘**（0.60×0.40），而 `object_points()` 用 0.70×0.50（外轮廓）
    → z 被系统性**高估 0.70/0.60 = +17%**，与观测几乎重合。
  - **方向是保守的**：z 高估 ⇒ `z ≤ cross(0.7)` 实际发生在真距离 ~0.6m ⇒ **冲刺触发得更贴门**（不是更早），
    所以它不增加撞门风险，只是把冲刺行程缩短一点。**当前先不动**。
  - 真要收口时：取一帧角点分别用 `frame_w = 0.70 / 0.60` 解 z，与「bbox 宽 + 实测开口宽」的 z 比。
    改 `geometry.frame_w` 等于改 z 标尺 = **动 A 路径**（`z.cross / z.slow_max / z.near_lost_m /
    width.z_max` 得一起重标），必须单独拍板。

  **为什么敢放宽**（不是「为了更容易过门」随手松的）：
  1. 收紧时 ALIGN 里 `surge=0`（只是原地对准），不达标就**耗到 `timeout_ms` = 该门 0 分**；
     放宽只是让「开始同时前进+修偏」提前，APPROACH 阶段 sway/heave **仍在闭环**（不是开环盲冲）；
  2. 计分规则（`.docwork_gate/rules.md:151`）：从门中间无接触通过 **30 分/个**，蹭到门仍有 **10 分/个**，
     方向错/没过 = 0 → 卡住不动的期望值最差，**略微蹭门仍远好于停在门外**；
  3. **关键：近距冲刺（出口① `z ≤ cross`）在代码里根本不看 `aligned`**（`gate_task.py::_on_pose`：
     `if z <= cross:` 只判 z 与 `cross_confirm_frames`）→ **收紧 `align` 对「防撞门」没有任何保护作用**；
     撞不撞由 `z.cross(0.7)` 与 `surge.through`（现 **0.6**）决定。
     所以「放宽 align」与「撞门风险」在当前代码结构下几乎是正交的两件事；
  4. 放宽的只是**「算作对准」的门槛**，不动冲刺速度、不动 `z.cross` 系列、不动直冲安全带
     ——回归守卫见 `test_safety_invariants_were_not_loosened` 与
     `test_align_threshold_is_loosened_but_shaped_like_margins`。
- **帧数**（未动）：`align.confirm_frames = 4`（8~11fps ≈ 0.4s 连续）。
  放宽范围是为了少进 HOLD、早点 creep/APPROACH；**不要靠降帧数来"更容易居中"**（那是防抖）。

**增益来源（2026-09-18 用户定）**：sway/heave/yaw 三套**共用小球那一套**（同一艘船、同一套推进器，

### 1.1 执行器传递特性：DOF 数字 ≠ 推力百分比（**必读**）

我们的 DOF 数字要经过三层变换才变成推力。按固件（`base/uart.py` + 下位机 `RC.c`/`Motor.c`）算出来：

```
DOF v → 轴字节 = 128 + 127·v            （mid 128 / range 127）
      → 下位机 Rc2MyRcKey(字节)          （>127: (b-127)/128·255；<127: (127-b)/127·255）
      → RC_Matching*(X)：**X ≤ 35 直接返回 0**，否则 ×0.9583
        （sway 走的是 **RC_Matching_Spin**：X≤35→0；35<X<150 用 0.555X-3.35；X≥150 用 1.666X-170）
      → 混控 allocation_matrix × RCStep（全局三档：aux_axis[5] = 0/1/2 → ×0.20/×0.24/×0.60 RCStepA）
```

实测（满杆 = `RC_Matching(255)` = 244）：

| DOF | heave | surge | **sway**（走 Spin 曲线，中段更弱） | yaw |
|---|---|---|---|---|
| 0.15 | 15% | 15% | 7% | 15% |
| 0.20 | 20% | 20% | 10% | 20% |
| 0.25 | 25% | 25% | 13% | 25% |
| 0.30 | 30% | 30% | 16% | 30% |
| 0.35 | 35% | 35% | 19% | 35% |
| 0.45 | 45% | 45% | 25% | 45% |
| 0.60 | 60% | 60% | 34% | 60% |
| 1.00 | 100% | 100% | 104% | 100% |

**四个通道的死区线都是 `|DOF| ≥ 0.138`** —— 低于它的命令被下位机当 0，一点推力都没有。

由此推出两条必须记住的结论：

1. **任何速度/增益档位都不能落在 (0, 0.138) 区间**。曾经 `surge.creep = surge.lost_backward = 0.12`
   → **有效推力 0%**：width/coarse 的"慢蠕进"、进近中的"轻微后退"其实一直站着没动
   （已提到 0.20；有不变量用例 `test_no_speed_preset_inside_actuator_deadzone` 守着）。
2. **PID 输出 = kp·误差**，所以误差一小、命令就落进死区 → **最后一截误差永远修不掉**：
   `pid_heave.kp=1.0` 时竖直误差 < 0.138 就等于没有推力（旧配置 `aligned` 要求 ≤ 0.05，
   数学上不可能达成 → 表现就是"肉眼已经差不多了，却一直 HOLD / 下潜没力气"；
   2026-09-18 把 `align.px_y` 放宽到 **0.26** 后不再自相矛盾——**对准带和死区带大幅重叠**，
   即"判对准时的残余误差本来就落在 actuator 推不动的那一截里"）。
   ⚠️ **上下不对称，而且继续放宽 `px_y` 解决不了它**：只有 `heave<0`（下潜）被 `dive_scale` 放大
   → 下潜的有效死区降到 0.138/2 ≈ **0.069**，**上浮仍是 0.138**。所以"门心偏上（dyn<0，
   需要上浮）且误差 < 0.138"是唯一真推不动的一档；若实船表现为"总差一点点上不去"，
   旋钮在 `ball.pid.kp`（把输出抬高过死区）或给上浮也加补偿，**不是继续放大 `px_y`**。
   对策 = **`comm.dof_comp`（下潜动力单独放大，底层共用）**：实现在 `base/uart.py::_apply_dive_boost`，
   位置在"限深保护之后、字节映射之前"，规则只有一条：**`heave < 0`（下潜）乘 `dive_scale`
   （默认 2.0）后夹到 [-1, 0]；上浮/悬停/平移/转向一律原样**。
   下潜偏弱就加大 `dive_scale`（3~4 更明显），冲过头就回 1.5；`enable: false` 回到原样。
   注意：很小的下潜指令（如 −0.05）即使放大也可能仍在死区(<0.138)内 —— 要连它都有效，
   `dive_scale` 得给足（≈3~4）。**两套任务（撞球/过门）共用这一套底层修正**（撞球同样受益）。

> 想让整体更猛：改 `frame.aux_axis[5]`（下位机三档灵敏度，全局 ×0.20/×0.24/×0.60，**连 surge 一起放大**），
> 或按上表把目标档位的 DOF 值往上抬。**都不是改下位机代码**。

### 1.2 水平修正通道：谁能动、谁推不动（2026-09-18 定量结论）

现场现象：「**coarse/width 往中间居中很费力**」「位姿档歪了调不动」。把两条死区线一起算就清楚了。

**第 ② 条死区线**（第 ① 条是 PID 内部 `deadzone`）：执行器死区 `|DOF| ≥ 0.138`（§1.1）。
通道能不能动，取决于 **`kp × 最小要修的误差` 是否 > 0.138**：

| 通道 | 增益（共用小球） | 命令 | **能动的最小误差** | 输出上限 | 上限对应的实际推力 |
|---|---|---|---|---|---|
| **sway** | `ball.approach_pid` kp **8.0** | `8.0·dxn`（夹 0.45） | **dxn > 0.017** | out_max 0.45 | **25%**（sway 走 Spin 曲线，中段天生更弱） |
| heave | `ball.pid` kp 1.0 | `1.0·dyn`（夹 1.0） | dyn > 0.138（下潜 ÷2 → 0.069） | out_max 1.0 | 100%（下潜再 ×2 后夹住） |
| yaw | `ball.edge_yaw_*` kp **0.3** | `0.3·误差`（夹 0.15） | **误差 > 0.46（近半个屏）** | out_max 0.15 | 15% |

结论（都写进了 cfg 注释与用例）：
1. **`align_yaw.in_px` 已由 true 改为 false** —— width/coarse 回到 **sway 为主**。
   原先用 yaw 居中，等于"只有门贴到画面边缘才有推力"，小误差时一点力都没有 → "很费力"。
   `in_px`/`in_pose` 打开时，**必须同时把 kp 抬过 `0.138/对准门槛`**，否则该通道是摆设
   ——不变量用例 `test_yaw_centering_channel_needs_gain_above_deadzone` 守着。
2. **水平方向唯一"随处可动"的通道是 sway**，但它的**上限只有 25% 推力**（Spin 曲线）
   ——这是"横移调不动"的天花板。要加强只能显式覆盖 `comm.gate.pid_sway.out_max`
   （0.45 → 0.8 时 Spin 曲线给到 ≈69%），代价是**与小球那套分叉**（共用增益用例会红，
   属有意分叉，需同步更新用例）。
3. yaw 是**方位**控制（把门拉到光轴上），**不是**姿态控制（机身与门法向平行）。
   修"歪"要靠下面的航向通道，不是靠 `dxn`。

### 1.3 p3p（3 角）的三条已知缺陷（真实 dump 实测）

`tools/analyze_pnp_center.py` / `tools/analyze_heading.py` 对录制角点（conf 0.7、reproj ≤20px）的统计：

| 项 | full（4 角） | **p3p（3 角）** |
|---|---|---|
| 最佳候选重投影 RMS | p50 6.8~10.2 px | **恒为 0.0 px**（p50=p90=0） |
| 深度 z（同场景） | 1.73 m | **1.25 m（−28%）** |
| 航向角 std（干净场景） | **5.4°** | **64~69°（不可用）** |
| 横向误差 `dxn`（对比 bbox 中心） | 偏差中位 −0.03~−0.04，0 帧符号相反 | 偏差中位 −0.054，**0 帧符号相反（可信）** |

要点：
1. **3 点解 6-DoF 是欠定的** → 最优解重投影误差恒为 0 → **`pnp.reproj_px` 在 p3p 下筛不掉任何东西**
   （它拦得住 full 的错解，拦不住 p3p 的）。所以 p3p 的 z/姿态不该当"测量值"用。
2. p3p 只能用两件事：**横向误差 `dxn`**（实测可信）和"这一帧有门"。
   ⇒ 航向通道**限定 `mode == full`**（有用例 `test_heading_channel_is_full_only_not_p3p` 守着）。
3. **p3p 求解需要上帧位姿做初值**（`geometry._iter_candidates`：`n==3` 且 `prev is None` → 无候选）。
   所以"冷启动只看到 3 个角"会直接退化 coarse；只有"从 full 掉一个角"才进得了 p3p。
4. 也因此 `z` 跳变保护（`max_z_jump_m=0.8`）在 full↔p3p 交替时会看到 ~0.5m 的 z 摆动
   （0.48m @1.7m，刚好在阈值内、不会被弃帧）→ 这只是"读数在抖"，不代表真靠近了。

### 1.4 航向通道：终于能判断"机身正不正"了

`dxn` 修**方位**（门在画面里偏多少 → 该横移），**航向**修**姿态**（机身与门法向差多少度 → 该转向）。
后者以前没有任何测量手段，现在用位姿档现成的 `rvec` 算：

```
n = R·[0,0,1]（门法向，相机系）→ psi = atan2(n_x, n_z)（度）；0 = 机身正对门
```

- **符号**（数值验证过）：机身右转 δ → `psi = −δ`；要修回来必须左转 ⇒ `yaw_cmd` 与 `psi` **同号**
  （与已验证的 `dxn` 通道同极性）。用例 `test_pose_heading_error_is_measured_and_signed_right`
  用"按指令方向转一步看 |psi| 是否变小"来钉，不是自证循环。
- **噪声**（真实 dump）：帧间 |Δpsi| p50≈3°、p90≈10°；EMA 4 帧（≈0.5s）后 ≈3°。
  ⇒ 只能做**慢速微调**，`deadzone_deg=6.0` 把噪声挡在外面。
- **偏置**：dump 里 psi 中位数 +12.3°，分不清是"场地门真的歪"还是"相机装歪"。
  ⇒ 默认 `heading.enable: false`，**只记录不控制**（日志/叠加里的 `hdg` 字段）。
  标定：把机身与门摆正，读几帧 `hdg` 中位数 → 写进 `bias_deg` → 再把 `enable` 打开。
- 开启后与 sway **并存**（位置→sway、姿态→yaw，信号不同，不违反"同一误差不重复放大"）。
- 一旦开启，**p3p 帧自动不参与**（§1.3 第 2 条）。

## 2. 相位与子状态：作用 / 运动 / 转移

> 每个状态都只做一件事，且**信息不足时宁可不前进**（`surge=0`）——这是水下"撞门不可逆"的代价函数决定的。

### 2.1 `SEARCH` —— 找门

| 项 | 内容 |
|---|---|
| **作用** | 视野里还没有可信门框（或刚放弃上一个门）：原地旋转扫视 |
| **运动** | `yaw = search.yaw(0.35)` 转 `search.spin_s(2.0)` 秒 → 停 `search.pause_s(1.0)` 秒 → 循环；`surge=sway=heave=0` |
| **进入** | 任务开始；ALIGN 失目标超 `pose_hold_frames`；REACQUIRE 超 `max_ms`；过完一个门（`pass_target>1`） |
| **离开** | 任一档拿到检测 → `ALIGN`（`_on_pose`/`_on_width`/`_on_coarse` 各自把自己推进 ALIGN） |
| **日志 `action`** | `search` |
| **理由** | 门无朝向要求、只看得到才动；`pause` 段静止检测比连续旋转更稳（运动模糊少） |

### 2.2 `ALIGN`（RANGE_ALIGN）—— 对准，不越线

四个子状态按**前端 mode** 与**门框占屏比**仲裁，同一相位内逐帧切换。

#### GOLDEN —— 位姿档对准（`full`/`p3p`，`gate_task.py:474-484`）

| 项 | 内容 |
|---|---|
| **作用** | 用 6-DoF 位姿把门框中心对到光轴上，**只横移/升降、不前进** |
| **运动** | 门框中心经 `camera.project((0,0,0), rvec, tvec)` 投影回图像得 `dxn/dyn`（归一化像素）；`sway = +PID_px(dxn)`（与 yaw 互斥，默认给 sway）、`heave = -PID_px(dyn)`、`surge=0` |
| **进入** | 本帧 `mode ∈ {full,p3p}` 且 `gate_pose` 返回非空（未触发直冲出口①时） |
| **离开** | `|dxn|,|dyn| ≤ align.px_x/px_y(**0.30/0.26**)` 连续 `align.confirm_frames(4)` 帧 → `APPROACH`；偏差出死区则 `_center_cnt` 清零重数。**与 width/coarse 档同一套判据** |
| **日志 `action`** | `center` |
| **理由** | 先"对准"再"前进"，把横向误差在静止状态消掉；撞球的 CENTER 相位同思路 |

#### CREEP —— 慢速靠近（出现三处）

| 来源 | 条件 | 运动 |
|---|---|---|
| width 档远距 | `aligned` 且 `z > width.z_max(1.5)` | `surge=surge.creep(0.12)` + heave + **水平：yaw 或 sway（互斥，默认 yaw）** |
| coarse 档对准 | `aligned` 且未达直冲条件 | `surge=surge.creep(0.12)` + **水平：yaw 或 sway（互斥，默认 yaw）** |
| coarse 档远距未对准（`:647-650`） | `ratio < coarse.far_ratio(0.18)` 且**没对准** | `surge=0`（只对中，`action=center`） |

| 项 | 内容 |
|---|---|
| **作用** | 信息不足（测距不可信/角点不全）时用**最低速**换取"更近、更多角点、更大占屏" |
| **进入** | 见上表 |
| **离开** | 拿到位姿 → GOLDEN；进入直冲窗口 → THROUGH；丢目标 → HOLD/SEARCH |
| **日志 `action`** | `creep` / `center` |
| **理由** | 0.12 的速度即使判断错也只蹭一下；**不用 `surge.slow`** 是为了留出反应距离 |

#### HOLD —— 信息不足就停在原地

| 项 | 内容 |
|---|---|
| **作用** | 角点/位姿不足，**不动**（保留对中微调），等下一帧信息变好 |
| **运动** | `surge=0`（heave 仍按偏差微调；水平 = yaw 或 sway，互斥） |
| **进入** | width 档：`aligned` 但 `z ≤ z_max` 且安全带确认还没攒够；coarse 档：未对准且 `far_ratio ≤ ratio`；丢目标后 `pose_hold_frames` 内 |
| **离开** | width/coarse 攒够对准确认 → THROUGH；coarse `_hold_cnt ≥ hold.max_frames(20)` → REACQUIRE；丢目标超防抖 → SEARCH |
| **日志 `action`** | `hold` |
| **理由** | "不动"是最便宜的安全动作；**注意 `_hold_cnt` 只在 coarse 的"未对准"分支累加**（width 档不累加，靠安全带出口脱困） |

#### REACQUIRE —— 短后退重取整门（`gate_task.py:668-729`）

| 项 | 内容 |
|---|---|
| **作用** | 门太近/角点被挡 → 退一点拉开距离，让 4 角重新出现 |
| **运动** | `surge = -surge.reacquire(0.25)`（**负值=后退**，方向待水池实测）；sway/heave 不参与 |
| **进入** | coarse：未对准且 `ratio > coarse.near_ratio(0.55)`（近距装不下）或中距 HOLD 超 `hold.max_frames` |
| **离开** | ① **闭环**：`ratio ≤ 进入时占比 × reacquire.stop_ratio(0.75)` → 回 HOLD（说明确实退开了）；② `reacquire.max_ms(800)` 到 → SEARCH；③ 连续次数 `> reacquire.max_times(2)` → **放弃后退**，原地 HOLD `reacquire.reset_after_ms(3000)` |
| **日志 `action`** | `reacquire` |
| **理由** | 旧版固定退满 2 s 导致"一直后退"；现在退到框变小就停，且**连续退无效就停手等**（倒影干扰时退也没用） |

### 2.3 `APPROACH` —— 前进（分两档）

| 项 | 内容 |
|---|---|
| **作用** | 已对准 → 前进接近，横向仍持续修正 |
| **运动** | 位姿档：`z > z.slow_max(1.3)` → `surge=surge.fast(0.35)`，否则 `surge=surge.slow(0.15)`；`sway/heave` 继续 PID |
| **进入** | GOLDEN 对准确认达标；width 档 CREEP 连续 `align.confirm_frames` 帧（`z>z_max`） |
| **离开** | `z ≤ z.cross(0.7)` 连确认 → THROUGH（出口①）；近距丢门 → THROUGH（出口②）；**角点退化到 coarse → 降回 ALIGN**（`:612-615`，避免盲冲） |
| **日志 `action`** | `forward_fast` / `forward_slow` |
| **理由** | 远快近慢是唯一的速度分级；`z.fast_max/align_max` 目前**未参与运算** |

### 2.4 `THROUGH` —— 冲过去（只前进，不修正）

| 项 | 内容 |
|---|---|
| **作用** | 已判定"该穿" → 直线前进穿越；**横向修正全部留在冲刺前**（冲刺中微调会放大抖动） |
| **运动** | `surge = 本次冲刺速度`（位姿档/近距丢失/门口兜底 = `surge.through(0.6)`；width = `width.surge(0.30)`；coarse = `coarse.surge(0.25)`）；`sway=heave=yaw=0` |
| **进入** | 四条直冲出口任一成立（见 §3） |
| **离开** | 进 THROUGH 后**计时**满 `through.confirm_ms(900)` → `pass+1`；达 `pass_target` → DONE(pass)；否则回 SEARCH 找下一个门。⚠️ 900ms 只是「旧 8 帧@9fps」的等价值，**够不够冲出去要按实测航速标定** |
| **日志 `action`** | `through` |
| **⚠️ 计数语义** | `_lost_cnt` 在 THROUGH 内**只增不减**（`_step` 提前 return 不清零）→ 判过门与"目标是否消失"无关，纯看帧数。8~11 fps 下 8 帧 ≈ 0.7~1.0 s；30 fps ≈ 0.27 s。**达 `pass_target` 立即 `neutral()` 停船**，没有额外前冲余量（实船实测有效，暂不改） |

### 2.5 `DONE` —— 终态

`_finish(reason)` 后每帧 `uart.neutral()` 幂等返回（`gate_task.py:299-303`）。`reason` 取值：

| reason | 触发 |
|---|---|
| `pass` | `pass_cnt ≥ pass_target` |
| `timeout` | `now - start ≥ comm.gate.timeout_ms(180000)` |
| `no_backend` | `hub.has_extra("gate")` 为假（权重缺失/未注册） |

- ③④ 的 `z`/`ratio` 只回答"**够不够近、该不该冲**"，**不参与闭环控制**（测距可信度不足以做闭环）。

  曾经本地写 0.3 而板端是 0.55，我整文件覆盖板端 cfg 时把它冲掉过两次 → 有不变量用例守着。
  **规矩：从此不再整文件覆盖板端 `cfg/*.yaml`，一律先 diff 再按 key 改。**

## 4. 参数手册

### 4.1 `cfg/comm.yaml → comm.gate.*`（运动与时序）

| 键 | 当前值 | 单位 | 作用 / 调大 / 调小 |

> 结果是"档位不会立刻降级"，防抖有利、对假门不利。

### 4.3 调参顺序（每次只改一个量，记录改前/改后）

1. **先标定，再调参**：卷尺深度曲线（0.5~6 m，判据 |误差| ≤10%）、门框真实尺寸、DOF 极性。
2. **速度类**（撞杆与否的第一旋钮）：`width.surge → coarse.surge → surge.through`（逐一往下降着试）。
3. **安全带类**（防上下/左右撞框）：`width.dy_max → coarse.dy_max → width.dx_max`（收紧方向最安全）。
4. **触发距离类**（决定"多早冲"）：`width.z_max → coarse.dash_ratio`。
5. **对准确认**：`width.confirm_frames` / `coarse.confirm_frames`（抖动大就加大）。
6. **退避类**（减少无谓后退）：`hold.max_frames ↑`、`reacquire.max_times ↓`（先别动 `max_ms`，它决定单次退多远）。
7. **下潜动力**（`comm.dof_comp.dive_scale`，底层共用、只影响 `heave<0`）：下潜偏弱就加大（2.0→3.0/4.0），冲过头就回 1.5。其余通道不受影响。
8. **保命参数**（`z.cross_confirm_frames`、`pnp.max_z_jump_m`、`z.near_lost_m`、`keypoint.conf_thr`、`depth_guard.min_depth_m=0.55`）：**只在给出"误判如何发生 / 代价 / 如何回退"之后才动；`min_depth_m` 是用户定死的，不动。**

## 6. 失效模式 × 现有对策

| 失效现象 | 可能原因 | 代码里的对策（参数） |
|---|---|---|
| 满速盲冲撞门/撞壁 | 单帧 PnP 错解给出小 z | `z.cross_confirm_frames` 连确认 + `pnp.max_z_jump_m` 弃帧 + ②的 `z.near_lost_m` 门槛 |
| 一直 coarse / 无位姿 | `recall_conf ≥ keypoint.conf_thr`（回忆点被当真） | 配置 0.45 < 0.5；启动日志会打这层关系 |
| 对准了却永远不前进 | 旧版 width 档近距 `surge=0` 卡死 | 出口③（`width.dash` 系列参数） |
| coarse/width 居中很费力 | yaw 默认增益推不动（0.3·dxn 要 >0.138 ⇒ 只有 dxn>0.46 有力） | 已改为 **sway 为主**（`in_px=false`）；若仍嫌慢 → 覆盖 `gate.pid_sway.out_max`（0.45→0.8，25%→69% 推力，属有意分叉） |
| 机身歪、调不动 | 位姿档只横移不转向（`in_pose=false`），而航向没人测 | 标定 `heading.bias_deg` 后开 `heading.enable`（只 full 生效）。**p3p 的航向不可用**（std 64°，见 §1.3） |
| 来回退、看着"一直后退又一直对准" | 一看框大就退 / 倒影干扰 | coarse 改"只有未对准才退"（`:647-666`）+ `reacquire.max_times/reset_after_ms/stop_ratio` |
| 门被倒影冒充 | 只按 score 选门 | `_pick_gate` 优先比角点数与置信度和 |
| 角点抖动导致档位乱跳 | 单帧角点忽有忽无 | `kpt_mem`（软融合）+ `align.confirm_frames` + `confirm_frames`（直冲计数） |
| 近距整门丢失被误判「已穿过」 | 目标被自身挡住/出画 | 出口②要求**近距**（`z ≤ near_lost_m` 或框占比 ≥ `near_lost_ratio`）；远距丢检仍走「轻微后退重锁」/SEARCH |
| **到门口突然 SEARCH、从没进 THROUGH** | width/coarse creep 无距离上限 → 船在 **ALIGN** 里到达门口；而出口②原先只管 APPROACH → 丢门只能回 SEARCH（0 分 + 原地旋转） | 已修：出口②扩到 ALIGN（见 §3 注）；回归用例 `test_align_near_lost_declares_pass_instead_of_search` + `test_align_far_lost_still_searches` |
| 判了 pass 却停在门前（没冲出去） | ①THROUGH 时长不够 ②起步太晚（在门口才起步）③`pass_target` 达标即停船 | 时长已改 2500；起步太晚要开 width/coarse 的 commit 出口（见下一行） |
| **到门口长期徘徊、不触发 THROUGH** | coarse/width 唯一能 commit 的出口③④被 `dash: false` 关掉 → 那两档**没有任何拍板通道**；只要整框还检测得到就一直是 `aligned → creep(0.20)` | 现场实测（`log/gate_run1.jsonl`）：占比 ≥0.60 的帧 **140/226=62%**、最长连续「在门口却没用冲刺速度」**18.7s**。已加**出口⑤「在门口超时兜底」**（`loiter.*`，3s 未 commit 就自己拍板）；判读指标 ⑦e 应降到 ≤1s。用例 `test_loiter_timeout_commits_through` 等 4 条 |
| 配置缺键直接崩 | 用 `AUV_CFG_DIR` 指向旧 cfg | 全部读取走 `_sub/_cfg/_num` 兜底（默认值=当前 cfg 值） |

## 7. 未验证 / 待标定（**不要当已验证用**）

1. `norm → m/s` 速度曲线、DOF 极性（sway/heave/surge 方向、REACQUIRE 后退方向）——台架点动实测。
2. 门框 `0.70 × 0.50` 是外缘还是开孔内缘；管径与悬挂高度实际值（影响所有米制阈值）。
3. 深度曲线：卷尺 0.5~6 m 比 `tvec.z`（判据 |误差| ≤10%），同时记录 ≥3 角点存活率。
4. width/coarse 直冲参数（`surge / dx_max / dy_max / z_max / dash_ratio / confirm_frames`）：
   **当前默认值是假设**，必须按"通过时无接触且不超时"标定。
5. 板端实际 fps（8~11 为实测口径）对 THROUGH 帧数计时的影响。
6. `body_center_offset`：未标定，且**未接线**（接进对准基准属改逻辑）。
7. `kpt_mem` 的 `k_sigma / recall_conf / conf_decay`：需真实倒影素材标定。

- **【想法·未实现，2026-09-18 用户提】** 对齐成功后把**完整三维信息存下来**（或只存 full 档那份），
  缺角时不去借「上一帧/历史帧」，而是借**已存好的三维**来辅助感知。工程评估：
  - 本质 = 把「逐帧位姿」升级成「**门位姿先验 / 重定位锚点**」，比 `prev`（上一帧，可能是 p3p 垃圾）稳。
  - **前提**：位姿是**相机系**的，船一直在动 ⇒ 锚点随时间失效。要么有里程/深度/推力模型推着走
    （本项目没有 DVL，只有深度遥测），要么只在「**船基本不动**」的窗口内用它 —— 而 ALIGN 正好
    `surge=0`，所以**ALIGN 内**可用（宽进近段不可用）。
  - 三条**免费**（不引入新状态机）的落地方式，按性价比排序：
    1. `prev` 只喂**最近一次 full 的位姿**（而不是最近一帧、更不是 p3p 的），做 IPPE 消歧/ITERATIVE 初值；
    2. 用存下来的 `z` 给 **p3p 的 z 做交叉校验**（p3p 的 reproj 恒 0 ⇒ 筛不掉错解，见 §1.3）；
    3. ALIGN 内若本帧只有 p3p，控制误差可退回「最近一次 full 的 `dxn`」（ALIGN 不动，误差不会突变）。
  - 结论：值得做，但**先要有 `AUV_TASK_LOG` 证明它真能改善**；现在先把「到门口回 SEARCH」这个真 bug 修掉。
