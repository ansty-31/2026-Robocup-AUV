## 2. 输出契约（**9 个张量**，缺一个就是补丁状态不对）

量化 bin 的输出 dtype 经 `hb_model_info` 确认为 **FLOAT（float32）×9**（hb_mapper 默认在输出前插了反量化，板端**无需**自己乘 scale）；
ONNX 侧为 **NHWC**。**顺序固定**（按尺度 P3/P4/P5，即 stride 8/16/32，每尺度一组 `bbox, cls, kpt`）：

| # | ONNX 名 | 形状 | 含义 |
|---|---|---|---|
| 0 | `output0` | `1×80×80×64` | stride **8** bbox：**DFL 原始 logits**，`4 边 × 16 bin` |
| 1 | `566` | `1×80×80×1` | stride 8 类别 logits（`nc=1`） |
| 2 | `567` | `1×80×80×12` | stride 8 关键点：`4 点 × (x, y, v)` |
| 3 | `656` | `1×40×40×64` | stride **16** bbox |
| 4 | `657` | `1×40×40×1` | stride 16 类别 |
| 5 | `658` | `1×40×40×12` | stride 16 关键点 |
| 6 | `747` | `1×20×20×64` | stride **32** bbox |
| 7 | `748` | `1×20×20×1` | stride 32 类别 |
| 8 | `749` | `1×20×20×12` | stride 32 关键点 |

- 尺度换算：`stride = 640 / 网格边长`（80→8、40→16、20→32）。
- 关键点通道顺序：`[x1,y1,v1, x2,y2,v2, x3,y3,v3, x4,y4,v4]`（**点优先**，已实测确认）。
- 角点顺序：**1=TL, 2=TR, 3=BR, 4=BL**（`kpt_shape: [4,3]`；`flip_idx: [0,1,2,3]` = 索引跟物理角点走）。
- 类别：pose 模型 `nc=1`，`names: ['gate']`。

## 3. 解码步骤（公式已实测验证）

> 验证方法：用 9 输出 ONNX 按下面公式手工解码，与 ultralytics 原版 `predict` 逐值对拍：
> **框最大偏差 0.40 px、角点最大偏差 0.009 px、置信度完全相同**（脚本流程见 §8「已做过的核验」）。

### 3.1 bbox（64 通道 = 4 边 × 16 bin，DFL）

```python
p = bbox[gy, gx].reshape(4, 16)          # 4 边顺序：left, top, right, bottom
p = softmax(p, axis=-1)                   # 在 16 个 bin 上做 softmax
d = (p * np.arange(16)).sum(-1)           # 期望 → 该边到网格中心的距离（单位 = cell）
cx, cy = gx + 0.5, gy + 0.5               # 网格中心（cell 单位；注意 +0.5）
x1 = (cx - d[0]) * stride;  y1 = (cy - d[1]) * stride
x2 = (cx + d[2]) * stride;  y2 = (cy + d[3]) * stride     # → 640 输入像素
```

### 3.2 类别（1 通道）

```python
score = sigmoid(cls[gy, gx])              # 板端工作点：score >= 0.6 才作为候选
```

### 3.3 关键点（12 通道）—— **最容易写错的一段**

```python
k = kpt[gy, gx].reshape(4, 3)             # 4 点 × (x, y, v)，点优先
x_px = k[i, 0] * stride                   # ★ x/y 在 ONNX 内部**已经**算成最终 cell 坐标！
y_px = k[i, 1] * stride                   #   不要再做 (raw*2 + 网格索引) —— 会算两遍
v    = sigmoid(k[i, 2])                   # v 是 raw logit，必须自行 sigmoid
```

**为什么**：导出用的补丁头（`scripts/3_export/modify_ultralytics.py --task pose`）已经把
`raw*2 + 网格索引` 烤进 ONNX（其中 `-0.5` 与 `make_anchors` 的 `+0.5` 相消）。
历史上有过把 `-0.5` 写进公式的版本，导致角点**系统性偏移 0.5 cell = 4/8/16 px**；这里以实测为准。

### 3.4 输出坐标系

- 上面所有 `*_px` 都在 **640×640 输入图**坐标系；
- 回溯原图：板端是 squish，所以 `x_orig = x_px * (W_orig / 640)`、`y_orig = y_px * (H_orig / 640)`；
- 去畸变已在预处理阶段做完，此处**不要**再做几何变换。

## 4. 后处理约束（本仓自设的工程约束，**不是**模型契约）

| 步骤 | 规则 | 常量 | 说明 |
|---|---|---|---|
| 候选 | `score ≥ conf` | **`conf = 0.6`** | 与评测/判定同工作点 |
| 角点可信 | 逐角点 `v ≥ V_MIN` | **`V_MIN = 0.8`** | 见 §7「低 v 的坐标不可信」 |
| 几何 | **不自交** + **顺序合法**（`TL.x<TR.x`、`BL.x<BR.x`、`TL.y<BL.y`、`TR.y<BR.y`） | — | 两条件在四角高 v 时几乎从不触发（实测 0~1.5%），留着是为了挡退化实例 |
| 去重（重复框） | **小框 conf 更低** 且 **≥2 条边重合** → 丢小框 | `EDGE_TOL=0.10`（× 小框短边）、`MIN_EDGES=2` | **不看「包含」**：远处第二个门可能落在近门框内，用包含会误删真门（实测误删 15 个） |
| 选门 | **近距离优先**；测距失败时选**置信度高**或**画面大**的 | — | 用户 2026-09-26 给定；本仓没有板端选门代码，板端请按此实现 |
| 语义 | 只有在四角都 `v ≥ V_MIN` 时才**当作完整门**去解 PnP | — | 角点在画面外时模型给低 v 是**正确行为**（标注约定 `Delete → v=0`），不是错 |

## 7. 已知坑（每条都有代价记录）

1. **kpt 的 x/y 不要再套公式**（§3.3）—— 套两次会让角点飞到画面外。
2. **低 v 角点的坐标没有意义**：v 是模型对"该角是否可见/可定位"的置信度。v 低时坐标是垃圾值，
   不要用它参与 PnP、也不要用它做"门中心"之类的推导。**门框不全时（部分可见）应降级处理，而不是丢整帧**。
   *实测：中水抽样 200 张里 62% 的帧"四角不齐"，但肉眼判定模型是**够用**的——因为看得见的角都对。*
3. **Softmax 必须在 BPU 上（int16）**：C2PSA 的 `/model.10/m/m.0/attn/Softmax` 若落在 CPU，
   模型会被切成多个 BPU 子图并留一堆 CPU 节点，延迟暴跌。这条已写进量化配置的 `node_info`，**别删**。
4. **6 输出 / 9 输出是硬契约**：导出前必须 `modify_ultralytics.py --task pose`（补丁版）；
   而**训练 / predict / val / 筛图必须用原版 head**（`--restore`）。训练脚本会自动「恢复 → 训练 → 重打补丁」，
   所以**训练完直接 predict 会崩**（`shape '[10,4,3]' is invalid`）——先 `--restore`。
5. **输入不要 letterbox**：板端是 squish；PC 侧 `prepare_calibration.py` 对非方形图会 letterbox 补灰边，
   所以校准集一律用**已经是 640×640 的 D+wb 图**，避免两套几何。
6. **量化后的 float32 输出**：bin 输出是 float32（不是 int8），板端不需要自己做反量化；
   但若上位机代码是按旧版 int8 输出写的，**必须改**。
7. **类别顺序错位是静默故障**：detect 三类顺序写错不会报错，只会让球/门/红球认反。

## 8. 量化与版本对应

| 轮 | 校准集 | 变更 | 输出层余弦 最小 | 逐节点 最小 / <0.95 个数 | stride32 kpt 中位/最小 | 结论 |
|---|---|---|---|---|---|---|
| R1 | `calibration_data/`（135：清水 70 + 中水 50 + 无门 15） | 基线 | 0.9074 | 0.9458 / 1 | 0.9786 / 0.9574 | |
| R2 | 同 R1 | `per_channel: True` | 0.9074（**逐位同 R1**） | 0.9458 / 1 | 同 R1 | 该选项对本模型**无效果**（损失来自激活量化） |
| R3 | `calibration_data_gate240_stage1_rgb/`（240：有门帧，**照 auv4 那代做法**） | 换校准集 | 0.9056 | 0.9519 / **0** | 0.9879 / 0.9705 | 逐节点达标 |
| **R4（采用）** | 同 R3 | 再把 head 末端 4 个卷积（bbox×2 + kpt×2）指 **int16** | **0.9058** | **0.9625 / 0** | **0.9985 / 0.9738** | **kpt 保真最好 → 采用** |

- 卡住"输出层最小余弦"的永远是 **bbox 的 DFL 原始 logits**（0.90~0.95）；那 64 通道是回归原始值，
  真正决定框位置的是**softmax 后的期望**（§3.1）——**该指标对本模型的框精度不敏感**，别用它一票否决。
- 参照：**上一代上线的 bin 同法测得 0.7862 / 0.9194（13 个节点 <0.95）** ⇒ 本次量化**明显更好**。
- **已作废**：2026-09-24 那轮"用 `max`/`mix` 校正方式优化"的尝试全部失败，
  记录已归档到 `_archive/quant_ideas_void_20260924/`，**禁止再试**（用户 2026-09-26 裁定）。
  从今以后：**只换校准集**迭代，`calibration_type` 固定 `default`。
- **已做过的核验**：① 解码公式 vs ultralytics 原版（框 0.40 px / 角点 0.009 px）✅；
  ② 量化保真（上面 4 轮的余弦，用 `scripts/3_export/check_quant_cos.py`）✅。
- **未验证（必须在板上做）**：
  * **帧率 / 延迟**：R4 把 4 个节点提到 int16，算力会涨，**必须实测**（若掉太多就退回 R3，R3 的 kpt 中位 0.988 也够用）；
  * **板端精度**：板端解码后的角点误差/PnP 稳定性，本仓没有板子，**一次都没实测过**；
  * **解码级 float↔量化 偏差**：本想用 hb_mapper 的 float/calibrated 两个 onnx 在容器里直接对拍，
    但实测**两者在同一输入下并不数值等价**（张量最大差 ~30），容器内这条路走不通 → 留待板上用真图对拍。
