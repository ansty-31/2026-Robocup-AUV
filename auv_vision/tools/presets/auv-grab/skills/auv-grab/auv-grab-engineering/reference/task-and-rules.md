# 任务口径、未知项与安全边界

> 本文件里 **✅ 已确认 / ❓ 未知 / ⚠️ 未验证** 三种标记是刻意的。看到 ❓ 就去问用户或去标定，不要把它读成"大概是这样"。

## 1. 任务口径（✅ 用户 2026-10-06 确认）

**RoboCup AUV 夹取任务 = 两个独立阶段：先夹小球，再夹小环。**

两个阶段是**独立**的含义要说清，因为它决定代码结构：

- 各自有**自己的感知目标**（阶段一红球，阶段二小环 —— 检测器不同，不只是换个阈值）；
- 各自有**自己的对准/接近/夹取时序**（判据、速度档、夹取动作、退出方式都可能不同）；
- 因此**不能**合成"一次接近、顺手夹两个"，也**不能**写成"同一条链换个 `kind` 就完事"。

工程里对应的是：`handling/percept/` 要长出**第二个感知目标**，决策层要长出**两段相位机**（或一条带阶段切换的相位机，但阶段边界必须是显式的）。

### 阶段一：夹小球（红球）

- 工程现状：**感知层已有并实测过**（`handling/percept/`），决策层没有。
- 复用现状：撞球任务（`task/ball.py`）的运动链是 `SEARCH → CENTER → APPROACH → DASH → STOP`，它是**撞**不是**夹**——DASH/STOP 那一段必须换掉，别直接抄。
- 夹取特有的量是**圆心与半径**（`detector.circles(frame)` / `Detection.cx,cy,r`），不是 bbox；要"够近了"这种判据用 `circle_to_ratio()`（按圆算面积占比），不要拿 bbox 占比（会把面积高估 4/π ≈ 1.27 倍）。

### 阶段二：夹小环

- 工程与文档里**零记录**：`grep -rn "小环\|圆环\|ring"` 在 `grab/` 与 `doc/` 里没有任何夹取相关的命中。
- ❓ **以下全部是未知，不许凭常识填**（见 §2 的问题清单）。
- 结构上它要落成"第二个感知目标 + 第二段时序"，与阶段一共用 `Det` 接口、`DetectorHub`、cfg 读取这些**公共件**，但检测算法不一定能复用红球那套（红球的整条链都建立在"红"这个先验上）。

## 2. ❓ 待确认清单（问用户 / 现场量；这是硬缺口）

### 2.1 小环的物理与外观（先要"是什么"，再谈算法）

| 要确认的 | 为什么它决定代码 |
|---|---|
| 颜色 / 是否多色、有没有包边或标记 | 决定能不能像红球一样用颜色掩膜，还是必须走形状（Hough / 轮廓圆度 / 椭圆拟合） |
| 材质与光学：不透光？半透明？强反光？ | 反光会像红球高光那样把目标打成环；半透明会污染掩膜内部 → 决定要不要填孔、怎么填 |
| 直径、截面圆环的**厚度**、像素尺度范围 | 决定 `r_min`/`r_max`、ROI 尺寸、以及"多近算够近"的像素判据 |
| 环在画面里的姿态：一定正对光轴，还是可能侧躺成椭圆 | 正对 → 圆拟合够用；侧躺 → 需要椭圆拟合或透视位姿，判据完全不同 |
| 夹取点在哪（环内壁？环外壁？底部？） | 决定"对准"的目标不是几何中心，而是夹爪能咬住的点 —— 这会改掉整条对准定义 |
| 是否会动（漂浮 / 被水流推动 / 被夹爪带跑） | 决定要不要跟踪预测（红球实测"被夹爪带走时 ≈40 px/帧"） |

### 2.2 夹爪机制（决定能不能下发指令）

| 要确认的 | 为什么它决定代码 |
|---|---|
| 夹爪由谁控制：STM32 自主（下位机在收到某个触发后自己闭合）还是上位机发指令 | 决定 `base/hw/uart.py` 要不要新增通道 |
| 若是上位机发：落在哪一字节/哪条通道 | 11B 帧**已被占满**：byte8/9 = 相对转角/取消（`0x80\|高7位`）、byte10 = 旋转编号。新增前必须确认下位机固件是否留了位，否则会与转帧互踩 |
| 闭合/张开的行程与耗时 | 决定"对准后停多久才夹"、以及要不要在夹取期间冻结运动 |
| 是否防水下误夹/卡住的自保护 | 决定失败重试边界（夹空一次要重试还是放弃） |
| 夹爪有没有状态回传 | 决定"夹到了没有"是猜的还是测的 |

### 2.3 任务约束

- 夹取阶段的总时间预算（撞球是 `comm.ball.timeout_ms: 30000`，夹取要另定）。
- 判分口径：夹住算分？放到指定位置才算？两个目标必须都成功还是可以放弃一个？
- 允许的动作范围：能不能原地转、能不能下潜（限深 0.55 m 是硬约束）、有没有禁入区。
- 顺序是否**必须**先球后环（用户口径是先球后环，但"必须"还是"可以交换"要确认）。

## 3. ✅ 已确认的安全与工程边界

- **限深保护不可改**：`comm.depth_guard.min_depth_m = 0.55`（现场定死）；深度 ≤ 0.55 m 时禁止上浮，只压 heave，surge/sway/yaw 不动。原因是"任何部位露出水面即本次比赛停止"。
- **不准动 BPU**：夹取走纯 CV，BPU 留给门 keypoint。
- **参数不硬编码**：视觉 → `cfg/vision.yaml` 的 `grab.*`；运动/时序 → `cfg/comm.yaml`；统一经 `base/cfg/settings.py` 读成 `S.vision.*` / `S.comm.*`；缺键要有代码兜底。
- **装配层唯一**：`main.py`。按 `grab/README.md` §4 的口径，决策层没设计完之前不要占状态机（`TASK_CLASS`/`TASK_CAM`/`TASK_STATE` 三处要一起加）。
- **跨工作区只读**：训练工程 `../RDKX5-YOLOv11n-/` 除测试脚本外一律只读。
- **子包依赖规则**：`grab/` 只 import `base` / `common` 与同级任务模块；`grab/__init__.py` 刻意不 eager import 子模块（为了 `grab.percept.cv_ball` 能脱离工程单独 import 做 PC 侧离线验证）——别为了"方便"加 eager import。

## 4. ⚠️ 未验证项（写代码时可以假定，但结论里必须标出来）

- 小环检测的一切精度/耗时数字（因为还没有检测器，也还没有素材基线）。
- 夹取阶段在水中的实际表现：推进器死区与极性、相机—机身安装偏置、水流对目标的影响、夹爪实际行程与夹持力。
- 把纯 CV 检测接到实时相机链路后的帧率（现有 25.6 / 64 ms 等数字都是**离线逐帧喂图**测的，不含相机 read 与显示开销）。
- 红球被黑瓦条遮挡只剩 1–3 px 红弧的漏检段（700 帧里约 43–55 帧）——靠"瓦条边缘 + 轨迹预测"解决，不是调阈值能解决的。

## 5. 判据怎么写才算"可验证"

每个阶段的判据都要能回答三个问题，答不出就说明判据还没定：

1. **量的定义**：用什么量判断"居中了 / 够近了 / 可以夹了"（像素偏差？半径？面积占比？多种投票？），单位与坐标系是什么（原图像素 / ROI 内归一化 / 位姿米）。
2. **阈值来源**：这个数是怎么来的（哪个素材集的哪分位数？现场量的？还是占位默认值）。占位值必须显式写"占位，待标定"。
3. **失效表现**：判据错了会怎样（提前夹空 / 撞上去 / 永远不夹 / 抖动卡死），以及对应的兜底（超时、丢目标惯性、重试上限、紧急停）。
